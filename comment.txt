The single most important structural fact

int_qa_paidsocial is long/tall format, not wide:

date | account_id_4c | account_name_4c | campaign_id | campaign_name |
channel | date_month | metric_name | conversions_4c | conversions_improvado | data_innovid

Every metric is a row identified by metric_name. conversions_4c / conversions_improvado are generic value columns that hold spend as well as conversions — spend is just metric_name = "spend".

This is why spend_4c is written as:

dax
spend_4c = CALCULATE(SUM(int_qa_paidsocial[conversions_4c]), int_qa_paidsocial[metric_name] = "spend")

Consequence: adding a new metric requires no model change and no new DAX. It's a new value in the metric_name column in BigQuery.

Answers to your specific questions:

- What represents Improvado? int_qa_paidsocial[conversions_improvado]. The legend textbox states explicitly: "Improvado data = mrt_paidsocial_pivot" — i.e. the Improvado side of the QA table is built from the same table the Data Export tab uses. That's why the QA and the Data Export numbers are directly comparable.
- What represents the reference/client data? int_qa_paidsocial[conversions_4c]. The legend says: "4C data = data comes from Social Ads Manager (Jordan Cross-Platform Pacing Report for Dashboard)". The Expanded Campaign Validation page titles the conversions_4c matrix "Innovid data by campaign" (5e7ec61a52c09c6576c9) and the conversions_improvado matrix "Improvado data by campaign" (9968d03217278a45e447). So _4c = Innovid / 4C = the expected/reference side.
- Where Spend comes from on each side: both sides, same table, same two columns — filtered to metric_name = "spend". There is no separate spend column.
- Where Conversions come from on each side: same two columns, filtered to metric_name <> "spend". ⚠️ This means conversions_4c is a sum across all non-spend metric_names at once — a heterogeneous total (QT + EC + CartStart + …). See §7 for why this matters.
- How campaigns are matched: Not in Power BI. int_qa_paidsocial carries a single campaign_id and a single campaign_name (no campaign_id_4c / campaign_id_improvado pair). The join is already resolved upstream in the BigQuery model. I cannot see the join key from the PBIP files.
- How dates are matched: same — a single date column, plus a derived date_month. Resolved upstream.
- Is account/channel part of the matching grain? The output grain is date × account_id_4c × account_name_4c × campaign_id × campaign_name × channel × metric_name. Account and channel columns are suffixed _4c, which strongly implies the 4C/Innovid values are canonical and the Improvado side was mapped onto them. Again, the actual join predicate lives in BigQuery, not in the PBIP.

Three consequences you should know about before anything changes

1. Adding the 5 metrics silently changes existing QA numbers. conversions_4c / conversions_improvado are defined as metric_name <> "spend" — i.e. everything that isn't spend. The moment 5 new metric_names land in BigQuery, the Conversions columns on the Channel, Date, Account and Campaign matrices all get larger and their % diff conv shifts. Any previously-agreed conversion match rate will move. This is not a bug you introduce — it's already how the model behaves — but it will surprise the client if nobody says so.
2. "Conversion variance" at campaign level is currently a heterogeneous sum. Adding QT + EC + CartStart + Leads + Activations into one number and taking a % of it is not what the client means by "Conversion variance > 5%". You need metric_name in the grain (slicer or matrix level) for that list to be defensible.
3. % diff spend is signed. A filter > 0.05 catches only campaigns where Innovid is higher. "Variance > 5%" must be ABS(...) > 0.05.

10. HOW WE WILL GET THE >5% CAMPAIGN LIST

Correct grain — and yes, campaign_name alone is not safe. The existing campaign matrix already uses campaign_name as level 1 and campaign_id as level 2 precisely because names collide (T-Mobile campaign names are long templated strings; the expansion state in the PBIP shows names like TMO_Postpaid_Voice_X_Perf_PSTPConv_Meta_Q2_2025_…_SOC-CMP-001 which differ only in trailing segments). The list must be keyed on campaign_id with campaign_name shown for readability.

Recommended grain for the deliverable:

campaign_id  (key)
campaign_name  (label)
channel        — available as slicer; add as a column since the same campaign_id
                 can appear under multiple channels in this table
account_name_4c — available as slicer; add as a column for traceability
date range     — set via the date / date_month slicers
metric_name    — required for the Conversions list; not applicable to Spend

Does "Expanded Campaign Validation" already solve part of this? Partly — but less than it looks. It gives you campaign × metric_name at the right grain, and it is the only place metric_name is broken out per campaign. But:
- It shows the two sides in two separate matrices (5e7ec61a52c09c6576c9 Innovid, 9968d03217278a45e447 Improvado), so you can't read a variance off it.
- It has no diff, no % diff, no icons, no threshold.
- So it solves grain, not variance. It cannot produce the >5% list.

The page that actually gets you 90% of the way is the General page campaign matrix 2ab350d58a1db8976358 — it already has campaign_name + campaign_id rows and all four spend variance measures. It needs exactly one thing: a >= 5% filter on the absolute variance.
